Give the world a player and a heartbeat: the vector camera pose, per-axis radius collision that slides along walls, and the requestAnimationFrame loop with a clamped delta-time. This is the plan where the two most silently-breakable properties in the project — frame-rate independence and no-tunneling collision — become mechanically asserted facts.

## Phase Goal

The player can move, strafe, run, and look around a hand-designed level with correct wall collision, validated on a top-down view before any 3D exists. (Phase 2's ROADMAP Goal is stated as an outcome rather than an "As a / I want to / so that" user story — see the planner return note.)

Purpose: The camera model chosen here is what Phase 3's raycaster is built on (D-01), and delta-time is the one thing PITFALLS calls out as unretrofittable — "bake dt in from first movement" — because retrofitting it later touches every motion call site (D-05). Per-axis radius collision is table stakes; combined-axis collision "feels terrible" and players notice immediately (D-06).
Output: `js/player.js` and `js/game.js` (the `Player` and `Game` globals), `CONFIG.DT_MAX`, a booting game loop, and a headless motion harness that proves the clamp and the no-tunneling property.
</objective>

  <behavior>
    - Spawning from the level puts the player at Level.playerStart with a unit direction and a camera plane of length CONFIG.FOV_PLANE that is perpendicular to it.
    - Rotating by any angle keeps the direction a unit vector, keeps the plane at length FOV_PLANE, keeps the two perpendicular, and preserves the plane-from-direction relationship exactly — after a thousand rotations as after one.
    - Holding forward for one simulated second moves the player WALK_SPEED cells along the direction vector, whether that second is delivered in 60 frames or in 500.
    - Holding forward and strafe together moves at exactly the same speed as holding forward alone (the intent vector is normalized), just in a diagonal direction.
    - The run modifier multiplies speed by RUN_MULT and nothing else.
    - Running head-on into a wall stops forward progress at the collision radius and leaves the player in a non-solid cell.
    - Running diagonally into a wall keeps the free axis moving and zeroes only the blocked axis (wall sliding).
    - After any sequence of frames, floor(x)/floor(y) is never a solid cell.
  </behavior>
  <action>
Add `DT_MAX: 0.05` to `CONFIG` in `js/config.js` with a comment naming it as the delta-time clamp that bounds the per-frame step (D-05). Change nothing else in config.js.

Create `js/player.js` attaching a global `Player` object. No DOM, no timers, no rendering — pure simulation state and math, so it runs unchanged in a Node vm sandbox.

STATE. `x`, `y` (world position, in cells), `dirX`, `dirY` (unit direction), `planeX`, `planeY` (camera plane). Tuning constants on the object with a one-line comment each: `RADIUS` 0.22 (collision radius in cells), `WALK_SPEED` 3.0 (cells per second), `RUN_MULT` 1.8, `TURN_SPEED` 2.6 (radians per second for keyboard turning), `MOUSE_SENSITIVITY` 0.0022 (radians per raw mouse pixel — event-based, deliberately NOT scaled by delta-time, per the PITFALLS note that mouse input is already per-event).

CAMERA MODEL (D-01 — locked, Phase 3 depends on it). The plane is always the direction rotated a quarter turn and scaled by the field of view: `planeX = dirY * CONFIG.FOV_PLANE` and `planeY = -dirX * CONFIG.FOV_PLANE`. Expose `Player.setDir(dx, dy)` which normalizes the given vector, stores it, and recomputes the plane from it — the single place that relationship is written. Expose `Player.rotate(a)`: compute `cos(a)` and `sin(a)` ONCE and apply the SAME 2D rotation matrix to both the direction and the plane (rotating both, rather than recomputing the plane, is what keeps this the standard raycaster camera and avoids per-column trig later). Positive `a` turns right. Do not store an authoritative angle; if a convenience angle is wanted for the top-down view, derive it on demand from the direction vector.

SPAWN. `Player.spawn()` reads `Level.playerStart` and sets `x`, `y` from it, then calls `setDir` with the start facing. If `Level.playerStart` is missing, fall back to the centre of the first non-solid cell found and record the fallback on `Player.spawnWarning`.

PER-AXIS COLLISION (D-06 — locked). Implement `Player.canOccupyX(nx, y)` and `Player.canOccupyY(x, ny)` as private-ish helpers, then `Player.moveBy(dx, dy)`:
  - For the X attempt: let `edge = nx + (dx > 0 ? RADIUS : -RADIUS)` be the leading edge; the move is rejected if `Level.isSolid(floor(edge), floor(y - RADIUS))` OR `Level.isSolid(floor(edge), floor(y + RADIUS))` — both corners of the leading edge, so the radius protects the corners as well as the centre line.
  - The Y attempt is the mirror image using `y`-leading edge and the two x-extreme corners.
  - Resolve X first and Y second, each accepted or rejected INDEPENDENTLY. Rejecting one axis must never cancel the other — that independence is exactly what produces natural wall sliding instead of sticking.
  - A zero delta on an axis skips that axis's test entirely.

UPDATE. `Player.update(dt, intent)` consumes the intent contract `{forward, strafe, turn, run, mouseDX}` (all numeric except `run`, a boolean):
  - Turning: apply `intent.turn * TURN_SPEED * dt` (keyboard turn, delta-time scaled) and then `intent.mouseDX * MOUSE_SENSITIVITY` (mouse turn, event-based, NOT delta-time scaled) through `Player.rotate`. Skip the call entirely when the total is zero.
  - Movement: build the local intent vector from `forward` and `strafe`. Derive the unit RIGHT vector by dividing the plane by `CONFIG.FOV_PLANE` — the plane is the authoritative source of "right", and dividing out the field-of-view length is what makes strafe speed equal forward speed regardless of FOV. Normalize the `(forward, strafe)` pair when both are non-zero so a diagonal is not faster than a straight line. Multiply by `WALK_SPEED`, by `RUN_MULT` when `intent.run` is set, and by `dt`. Feed the resulting world delta into `moveBy`.
  - Guard non-finite `dt` or intent values by returning without moving, so one bad number can never corrupt the pose.

TUNNELING BUDGET. Expose `Player.maxStepPerFrame()` returning `WALK_SPEED * RUN_MULT * CONFIG.DT_MAX`. Add a comment stating the invariant: because the collision test is at the LEADING EDGE of the destination and walls are one cell thick, tunneling requires a single-frame step of at least one full cell, and this value must stay well below 1.0. Do not hardcode the number — derive it, so retuning the speed constants keeps the invariant honest.
  </action>

Create `js/game.js` attaching a global `Game` object — the orchestrator that owns the frame.

STATE. `running` (boolean), `last` (previous frame timestamp in milliseconds), `dt` (last clamped delta in seconds), `time` (accumulated simulated seconds), `frames` (count), `rafId`, and `resync` (a boolean flag described below).

SEAMS (this is why the loop is written before its consumers exist). `Game.input` defaults to `null` and, when assigned by Plan 03, must be an object exposing `readIntent()` returning the intent record. `Game.view` defaults to `null` and, when assigned, must be an object exposing `render()` that writes into `Framebuffer.buf32` and does NOT present. `Game.ZERO_INTENT` is a frozen intent record with `forward`, `strafe`, `turn`, `mouseDX` all 0 and `run` false, used whenever no input source is attached.

FRAME (PLAT-04, D-05 — locked). `Game.frame(now)`:
  - Return immediately when not running.
  - When `resync` is set, store `last = now`, clear the flag, use a delta of 0 for this frame and skip straight to scheduling — this is the clock-domain-safe way to absorb a tab refocus without mixing timestamp sources.
  - Otherwise compute `raw = (now - last) / 1000`; coerce a non-finite or negative value to 0 (a backwards clock must never move the player backwards); then `dt = raw > CONFIG.DT_MAX ? CONFIG.DT_MAX : raw`. THE CLAMP IS THE WHOLE POINT: an unclamped delta after a tab switch or a garbage-collection pause is the documented tunneling source, and the clamp is what bounds one frame's movement to well under one cell.
  - Store `last = now`, accumulate `time += dt`, increment `frames`, then call `Game.step(dt)` and `Game.render()`, then schedule the next frame.
  - Bind the frame callback once at module scope and reuse it, so scheduling allocates nothing per frame.

STEP. `Game.step(dt)` reads the intent — `Game.input ? Game.input.readIntent() : Game.ZERO_INTENT` — and passes it with `dt` to `Player.update`. Nothing else this phase; later phases add entity and weapon updates here.

RENDER. `Game.render()` calls `Game.view.render()` when a view is attached, otherwise fills the framebuffer with `CONFIG.CLEAR_COLOR`; then performs exactly ONE `Framebuffer.present()`. Keeping the present in the loop rather than in each view is what guarantees Phase 1's single-blit-per-frame contract survives every future view swap.

CONTROL. `Game.start()` sets `running`, sets `resync`, and schedules the first frame; it is idempotent (a second call while running is a no-op). `Game.stop()` clears `running` and cancels the pending frame. `Game.attach()` registers the resync triggers: a `visibilitychange` listener that sets `resync` when the document becomes visible, and a window `focus` listener that does the same. Both must also call `Game.input.reset()` when the attached input source exposes one, so a key held at the moment focus was lost cannot stay stuck down — belt and braces alongside the clamp.

WIRING. In `js/main.js`, on window load: initialise the framebuffer as today, build the textures and sprites as today, then call `Level.build()`, `Player.spawn()`, `Game.attach()` and `Game.start()`. Stop calling `Preview.render()` as the persistent screen — the running loop now owns what is on screen — but leave `js/preview.js` loaded, since `Preview.blit` remains the reference color-keyed blit for Phase 4. The resize handler must call `Framebuffer.resize()` only; the loop repaints on the very next frame, so no manual repaint is needed any more.

Register `js/player.js` and `js/game.js` in `index.html` as classic script tags: `js/player.js` immediately after `js/level.js`, and `js/game.js` after it but still before `js/main.js`. Extend the load-order contract comment to name both new files, state that `Game.input` and `Game.view` are the two seams Plan 03 fills and Phase 3 re-points at the raycaster, and state that the delta-time clamp lives in `CONFIG.DT_MAX`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser scheduler <-> game loop | The frame timestamp is supplied by the platform and is NOT trustworthy in magnitude — a backgrounded tab, a garbage-collection pause or a throttled CPU can deliver an arbitrarily large delta. |
| intent source <-> simulation | Plan 03 will attach a live input object to `Game.input`; the loop must tolerate it being absent, incomplete or supplying non-finite numbers. |
| world position <-> grid indices | Player coordinates are floats that get floored into `Level.cells` indices; a non-finite coordinate would produce a garbage index. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06 | Denial of Service | unbounded frame delta after tab refocus or a GC pause | high | mitigate | `dt = min(raw, CONFIG.DT_MAX)` plus a resync flag on visibility/focus; Task 3 assertions 2 and 5 drive a two-second and a hundred-second raw delta and prove the player stays inside the level. |
| T-02-07 | Tampering | movement crossing a wall (tunneling) at run speed | high | mitigate | Leading-edge collision test plus the derived `maxStepPerFrame()` invariant kept under 0.5 cells against a one-cell wall thickness; Task 3 assertions 3, 5 and 6 assert the budget and 5000 randomized frames never end inside geometry. |
| T-02-08 | Tampering | non-finite or negative delta / intent corrupting the pose | medium | mitigate | Non-finite and negative raw deltas coerce to 0 in the loop; `Player.update` returns without moving on any non-finite input; Task 3 assertion 2 drives both cases and asserts the pose stays finite. |
| T-02-09 | Denial of Service | per-frame allocation causing GC hitches in the hot loop | low | mitigate | The frame callback is bound once, `ZERO_INTENT` is a shared frozen record, and no array or object is created per frame; Phase 1's preallocate-once framebuffer is reused untouched. |
| T-02-10 | Tampering | a missing or malformed `Game.input` seam | low | mitigate | The loop falls back to `ZERO_INTENT` when no input source is attached and only calls `reset()` when the source exposes it; Task 3 assertion 13 runs the loop with both seams null. |
| T-02-SC | Tampering (supply chain) | npm/pip/cargo installs | low | accept | Zero dependencies, no package manager, no install step (PLAT-01). Node runs the harnesses using built-in modules only. |
