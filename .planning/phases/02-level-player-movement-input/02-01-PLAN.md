  <name>Task 1: Hand-designed grid level — parser, forced-solid border, wall-ID to texture table, marker tables</name>
  <files>Doom/Claude Opus 4.8/GSD/js/level.js, Doom/Claude Opus 4.8/GSD/index.html</files>
  <action>
Create `js/level.js` attaching a single global `Level` object. Keep it pure data plus synchronous parsing — no DOM, no canvas, no timers — so it runs unchanged inside a Node vm sandbox.

AUTHORED SOURCE (D-02). `Level.SOURCE` is an array of equal-length strings, one per grid row, authored for readability. Target roughly 24 rows of 24 characters. The map must contain, and the harness will assert:
  - at least three separate rooms, where a room is provable as a 4x4 block of contiguous floor cells, and the three blocks are mutually disjoint;
  - at least one one-cell-wide corridor cell (a floor cell whose two x-neighbours are both solid, or whose two y-neighbours are both solid);
  - at least one occurrence of every one of the five wall materials;
  - a dead-end alcove faced with the exit material, so Phase 6 has somewhere to put the exit;
  - full connectivity: every floor cell and every marker is walkable from the player start.
Design it as a small connected complex: a west starting room, a north-east hall, a south chamber, joined by narrow corridors, with a couple of internal pillars so the top-down view (and later the raycaster) has geometry to look at.

LEGEND (data, not scattered literals). `Level.WALL_CHARS` maps the five wall characters to wall IDs: `'#'` stone = 1, `'%'` brick = 2, `'='` tech = 3, `'+'` door = 4, `'!'` exit = 5. `Level.FLOOR_CHARS` is the string of characters meaning open floor (a period and a space). `Level.MARKER_CHARS` maps marker characters to spawn type strings: `'P'` player, `'E'` enemy, `'h'` health, `'r'` armor, `'m'` ammo, `'g'` shotgun, `'X'` exit. Marker cells are floor — the marker is metadata about the cell, never a wall (D-04).

WALL-ID TO TEXTURE TABLE (D-03 — Phase 1 left this as a comment; materialize it). `Level.WALL_TEXTURES` is an array indexed by wall ID whose element 0 is `null` (index 0 unambiguously means "no wall") and whose elements 1..5 are the strings `'stone'`, `'brick'`, `'tech'`, `'door'`, `'exit'` — all keys of `Textures.map`. Expose `Level.textureNameFor(id)` returning the string or `null`, and `Level.textureFor(id)` returning `Textures.map[name]` or `null`. Resolve `Textures.map` lazily inside the function body so level.js has no load-order dependency on textures.js. Also expose `Level.validateTextures()` returning an array of wall-ID/name pairs whose texture is missing from `Textures.map` — an empty array means the table is fully wired.

PARSING (`Level.build()`, idempotent — calling it twice must produce byte-identical cells). Derive `Level.WIDTH` as the longest source row length and `Level.HEIGHT` as the source row count. Allocate `Level.cells` as a `Uint8Array(WIDTH*HEIGHT)` addressed row-major with index `my*WIDTH + mx`. For each row: pad short rows with the stone character and truncate long rows, so a ragged hand-edit cannot shift the grid (D-02). For each character: a wall character writes its ID; a floor character writes 0; a marker character writes 0 AND records the marker; anything unrecognised writes 0 and pushes a descriptive string onto `Level.warnings` (which starts empty on every build, so the harness can assert the shipped map parses with zero warnings).

FORCED BORDER (D-02). After the character pass, unconditionally overwrite the entire outer ring — row 0, row HEIGHT-1, column 0, column WIDTH-1 — with the stone wall ID. This runs last, so no authored character and no ragged row can leave a gap in the border.

MARKER TABLES (D-04). The `'P'` marker sets `Level.playerStart` to an object with `x` and `y` at the cell centre (`mx + 0.5`, `my + 0.5`) plus `dirX`/`dirY` copied from `Level.START_FACING` (a module-level constant; default facing east, `{x:1, y:0}`, a unit vector). If more than one player marker exists, keep the first and record a warning. Every other marker pushes `{type, x, y, mx, my}` onto `Level.spawns` (reset to an empty array on every build). Only the player start is consumed this phase; `Level.spawns` is the table Phase 5 will read.

QUERY API. `Level.cellAt(mx,my)` returns the wall ID, returning the stone ID for any out-of-bounds coordinate. `Level.isSolid(mx,my)` returns `Level.cellAt(mx,my) > 0` and therefore returns TRUE for every out-of-bounds coordinate — this is the guard that makes leaving the grid impossible for Plan 02's collision resolver. Both take integer cell coordinates; callers floor world coordinates before calling.

Register `js/level.js` in `index.html` as a classic `<script src>` placed AFTER `js/preview.js` and BEFORE `js/main.js`, and extend the existing load-order contract comment to name the new file and its position (D-10). Do not touch any other script tag.

LINE OF SIGHT. Add `Level.lineOfSight(x0, y0, x1, y1)` to `js/level.js`: a grid DDA march in world coordinates returning `true` when no solid cell lies strictly between the two points. Use the same traversal shape Phase 3's wall pass and Phase 5's hitscan will use, so the code is one technique learned once: compute the ray direction from the two points, derive per-axis `deltaDist` as the absolute reciprocal of each direction component (substituting a large finite constant such as 1e30 when a component is zero, rather than relying on Infinity arithmetic), initialise `sideDist` from the fractional position inside the starting cell, then repeatedly step to whichever axis has the smaller `sideDist`. Stop and return `true` when the marched cell equals the destination cell; return `false` the moment a solid cell is entered. Guard the degenerate case where both points are in the same cell by returning `true` immediately, and bound the loop with an iteration cap of `WIDTH + HEIGHT + 2` steps returning `false` if it is ever exhausted, so a pathological input can never spin. The function must be symmetric in its two endpoints for open lines.

HARNESS BOOTSTRAP. Create `tools/boot.cjs`, a Node CommonJS module (the `.cjs` extension keeps it unambiguously Node-side; nothing under `tools/` is ever referenced by index.html, so the browser never sees it). It exports one function `boot(options)` that:
  - reads `index.html` from the game directory and extracts the ordered list of classic script sources by regular expression, exposing it as `scriptOrder` so harnesses assert the SHIPPED load order rather than a hand-written list;
  - builds a stub DOM in a `vm` context: a `document` with `getElementById` returning canvas stubs for `game` and `hud`, a `createElement` returning the same stub shape, a settable `pointerLockElement` (default `null`), and `addEventListener` recording handlers by type; a canvas stub whose `getContext('2d')` returns an object with `createImageData(w,h)` returning `{width, height, data: new Uint8ClampedArray(w*h*4)}`, a `putImageData` that increments a counter and records the last argument, plus no-op drawing methods and a `requestPointerLock` that records the call and resolves; and a `window` with `innerWidth`/`innerHeight` (default 1280x720, overridable), `addEventListener` recording handlers, and `performance.now()`;
  - stubs `requestAnimationFrame`/`cancelAnimationFrame` as a manual scheduler rather than a real timer: queued callbacks are held and only run when the harness calls the exported `raf.step(deltaMs)` or `raf.run(frames, deltaMs)`, which advance a virtual clock and invoke the pending callback with the virtual timestamp. This is what makes the game loop deterministically drivable and lets a harness manufacture an arbitrarily large frame delta;
  - evaluates each script source file in that shared context in the shipped order using `vm.runInContext`, so the harness exercises the real files;
  - exposes helpers on the returned object: `sandbox` (the globals), `raf`, `putCount()`, `fireLoad()` dispatching the recorded window `load` handlers, `dispatch(target, type, eventObject)` invoking the recorded handlers for a type, and `setPointerLockElement(el)`;
  - accepts `options.only` (an array of script basenames) so a harness can load a subset — for example just config, framebuffer, textures and level — without booting the whole game.
Add a `assert(condition, label)` helper export that prints `PASS` or `FAIL` with the label, tracks a failure count, and an `finish(token)` export that prints the given all-pass token only when the failure count is zero and exits with a non-zero status otherwise.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authored map source <-> parsed grid | Hand-authored ASCII rows are the only "external" input in this offline game; a ragged or mistyped row is the realistic way the world grid becomes malformed. |
| browser <-> local files (file://) | The page must load ONLY its co-located `js/` and `style.css`; a remote or module-loader reference would break offline self-containment (PLAT-02, PLAT-03). |
| grid queries <-> typed array indices | `cells` is a flat `Uint8Array`; an unguarded out-of-range index reads `undefined`, which compares as not-solid and would silently let the player leave the world. |
